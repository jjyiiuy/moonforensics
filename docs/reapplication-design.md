# 复审改进设计：应用服务离线事故复盘

本设计回应“定位模糊、统一抽象不清楚、通用关联缺少边界、应用价值不足”的初审意见。
它是实现与验收的契约；当前实现已覆盖统一事件适配和最小 CLI 链路，案件级文件 I/O
与完整报告编排仍明确留在后续范围。

## 1. 先解决一个明确问题

目标用户是开发者、值班运维和发布负责人。主问题是：
**在一批已导出的证据中，同一服务或实例的变更、异常和恢复分别发生在何时，依据在哪里？**
主场景为发布或配置变更后的异常复盘；崩溃重启和性能退化复用同一事件抽象。

输入是单次案件内的 UTF-8 文本、JSONL 及调用方提供的来源和映射配置。
输出是可重复生成的时间线、候选关联组、规则发现、证据索引与限制说明。
不替代日志检索或监控平台，不提供任意格式自动理解、实时监控和自动根因判定。

## 2. 价值以交付物说明

| 使用者的工作 | 手工做法 | 项目应交付的结果 |
| --- | --- | --- |
| 值班人员交接事故 | 对齐时间、复制日志、补来源说明 | 排序稳定、能定位原始证据的案件报告 |
| 发布负责人复核变更 | 分别检查变更、健康检查和回滚记录 | 同一服务范围内的候选组及完整时间线 |
| 开发者重复调查 | 对同一批日志重复筛选 | 固定输入与映射配置下内容一致的 Markdown/JSON |
| 团队核对材料版本 | 难以确认报告使用的日志版本 | 对原始字节进行摘要比对，内容变动明确失败 |

离线适合生产访问受限、证据需脱敏交接、或故障结束后仍需复核材料的情况。
当前没有生产用户研究和收益数据，不声称节省某个百分比的时间。
清单只证明内容与给定摘要一致，不证明证据来源真实，也不替代签名或可信存储。

## 3. 可复用的统一事件契约

公共 `IncidentEvent` 适配结果保留以下字段；它是分析核心与输入格式之间的稳定边界。

| 字段 | 语义与约束 | 现有实现与差距 |
| --- | --- | --- |
| `event_id` | 案件内稳定 ID，可由证据 ID 和物理行号构成，不能依赖当前时间 | `IncidentEvent` 已携带 |
| `timestamp` | 保留原时间，RFC 3339 统一为 UTC；无效时间诊断，缺失不猜测 | 已有 `NormalizedTimestamp` |
| `source_id` | 系统、组件与可选主机规范化；两来源必须有实际区别 | 已有 `NormalizedEvent` 和来源标准化 |
| `resource_id` | 案件内约定的服务或实例分析键，粒度必须明确 | 已有 `CorrelationEvent.resource_id` |
| `kind` | `Change / Alert / Crash / Other`，角色与严重级别分开 | 已有 `CorrelationKind` |
| `severity` | 标准级别或未知值；ERROR 不自动等于崩溃 | 已有 `Severity` |
| `evidence_ref` | 证据 ID、路径、物理行号与原始字节的定位关系 | `IncidentEvent` 已保留证据 ID/行号和原文；路径由案件层补充 |
| `attributes` | 指标、配置键、前后值、退出码等，未知字段保留 | JSONL 对象已保留在 `IncidentEvent.attributes` |

输入差异由适配层承担；排序、过滤、关联与报告消费约定好的事件。
“通用”是分析核心不依赖供应商字段名，不是无需配置就理解任何数据。

### 三类输入的映射责任

| 输入 | 显式映射 | 角色与保留属性 |
| --- | --- | --- |
| 配置 JSONL | 时间字段；配置资源再经映射选择服务范围 | `Change`；前后值与修订号 |
| 健康检查固定文本 | 声明时间和级别位置，由该格式适配器提取服务/实例 | 失败可为 `Alert`；延迟与原因 |
| 进程或指标 JSONL | 时间、来源、资源按声明字段取值；角色由格式配置指定 | 退出可为 `Crash`，指标为 `Other("metric")`；退出码与数值 |

`parse_jsonl` 当前只解析对象，不验证业务字段；`parse_plain_text` 只拆行，不理解任意文本。
文本解析会去除行尾空白，完整性必须基于原始字节，不能基于解析后的文本。
未声明的文本格式可保存为原始记录，但不能承诺自动识别时间、资源和角色。

### 资源映射是关联成立的前提

配置项 `orders-api/database.pool.max` 与实例 `orders-api-01` 不是同一种资源。
只有调查者声明二者属于本案件的服务范围 `service:orders-api`，才能在该范围关联。
必须保留来源资源及映射配置，以便复核为什么两条记录被归在一起。

案件也可选择 `instance:orders-api-01` 粒度，但服务级变更不能未经明确分配就落到该实例。
不通过名称前缀、消息关键词或相似字符串推测资源身份。
跨案件、不同环境、不同粒度不能默认合并；别名映射只统一身份，不构造服务依赖图。

## 4. 关联条件与分析边界

当前 `correlate_events(events, window_seconds)` 的实际语义：

1. 按标准化时间稳定排序，同时间保留输入顺序。
2. 选未消费的最早事件为锚点，收集资源键相同且位于闭区间 `[t0, t0 + W]` 的事件。
3. 至少两个不同来源才形成组；成员进入组后不重复消费。
4. 缺时间不参与关联，负窗口报错；不会把相邻小窗口传递拼成无限大的链。

当前核心不验证资源粒度或来源身份，调用方必须先声明；JSONL/文本适配层已拒绝空资源键，
没有资源的事件只保留在时间线中，不能让两个空键成为“同一资源”。
规则引擎目前只按单事件级别和文本片段匹配，不支持指标阈值、统计分析或变更后故障序列规则。
候选组先供人工复核；新增多事件规则必须另行定义并测试前后关系。
同组不等于变更造成故障，回滚后恢复也不能单独证明因果。

## 5. 三个可复现应用场景

均为仓库内虚构演示，不是生产事故证明；复用同一事件契约与关联函数。

### A. 连接池变更与健康检查失败

- 使用者：值班工程师和发布负责人。
- 输入：`samples/incidents/config-change/changes.jsonl` 与 `health.log`。
- 事实：09:00:00 连接池从 40 改为 4；09:00:40 检查失败；09:02:00 回滚，09:02:30 恢复。
- 映射：配置项与健康检查显式映射到 `service:orders-api`；变更为 `Change`，失败为 `Alert`。
- 操作与输出：取三分钟窗口，报告引用上述记录，列出“变更可能相关”而非“根因确认”；恢复在完整时间线上可见。
- 用途：事故交接与发布复核；工具不自动执行回滚。

### B. 应用错误与进程非零退出

- 使用者：开发者和服务维护者。
- 输入：`samples/incidents/service-crash/app.log` 与 `process-events.jsonl`。
- 事实：10:03:13 有错误；10:03:14 进程退出；10:03:24 替换进程运行。
- 映射：调用方明确日志所属实例 `instance:checkout-api-01`；日志与退出记录来自不同来源。
- 操作与输出：五秒窗口关联错误和退出，十秒后的重启不纳入五秒组，但在完整时间线展示。
- 用途：定位需核查的错误上下文；退出码或相邻错误不能直接证明 OOM 或代码根因。

### C. 指标异常与网关超时

- 使用者：运维人员与接口负责人。
- 输入：`samples/incidents/performance-degradation/metrics.jsonl` 与 `gateway.log`。
- 事实：14:22:00 CPU 为 91%、P95 为 1450 ms；14:23:17 网关超时。
- 映射：二者映射到 `instance:catalog-api-02`，指标为 `Other("metric")`，超时为 `Alert`。
- 操作与输出：两分钟窗口生成候选组，保留 CPU、内存和延迟供对照；窗口外记录不进入同组。
- 用途：确定继续调查的时段和材料，不替代指标平台或自动认定 CPU 根因。

## 6. 现状、缺口与实现顺序

| 状态 | 内容 |
| --- | --- |
| 已实现库原语 | 模型、解析、标准化、清单校验、时间线、单事件规则、资源关联和报告 |
| 已补齐 1 | `IncidentEvent` 适配结果：解析记录直接生成事件，保留属性、行号和诊断 |
| 已补齐 2 | 显式字段/资源映射：JSONL 与固定文本适配器验证必填字段和资源粒度 |
| 已补齐 3 | CLI `analyze` 贯通适配、时间线和候选关联；`verify` 支持可选摘要比对 |
| 仍需补齐 | 三场景全部改为实际文件输入，贯通完整报告与已有清单的案件级流程 |
| 验收交付 | 三场景实际文件输入、报告黄金文件、负向测试和完整使用说明 |

不提前实现供应商插件、机器学习、依赖图、在线服务或 GUI。
不以宣传词或提交数量代替实现。

## 7. 复审必须展示的验收证据

- 场景文件内容直接生成分析事件，不再手工抄写时间、资源和消息。
- 修改供应商字段名并调整映射后，同一逻辑事件产生相同结果，证明分析核心可复用。
- 不同资源、同来源、窗口外、缺时间、空资源、映射冲突分别有负向测试。
- 发现可追溯到证据 ID 和行号，未知业务属性保留；原始字节与派生文本分开处理。
- 固定输入、配置与规则，重复运行的 Markdown/JSON 输出一致。
- 字节被修改后与先前清单比对失败，不将重新计算新摘要当作校验成功。
- 提供三份报告并标明数据虚构，不宣称生产采用率或未经测量的收益。
