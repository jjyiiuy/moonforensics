# MoonForensics 项目范围与验收契约

> 状态：原第 1 次提交的范围基线，已根据初审意见收敛定位
>
> 工作名称：MoonForensics / 应用服务离线故障复盘工具
>
> 统一事件契约、实际实现缺口和复审验收见 [复审改进设计](reapplication-design.md)。

## 1. 项目问题

系统故障发生后，日志、监控快照、配置变更和人工记录通常散落在不同文件中，
时间格式与严重级别也不一致。排障人员需要手工整理时间线，难以证明报告中的
每条结论来自哪份原始证据，也难以稳定复现同一次分析。

MoonForensics 聚焦应用服务的离线事故复盘，以发布或配置变更后的异常调查为主场景。
它回答同一服务或实例的变更、异常和恢复分别发生在何时、依据在哪里。
资源身份和字段映射由调用方明确提供，核心复用标准化事件、稳定时间线与窗口关联，
不承诺自动理解任意日志。候选关联组与根因结论分开，供调查人员继续复核。

首版是工程故障分析工具，不宣称满足司法取证、电子数据鉴定或安全事件响应的
全部合规要求。

## 2. 目标用户

- 需要复盘服务崩溃、性能退化或错误配置的开发者。
- 需要把多来源事件整理成交接材料的运维与站点可靠性工程师。
- 需要一个可测试的 MoonBit 离线日志分析示例的库作者。

## 3. 三个完整使用场景

### 3.1 服务异常退出

用户导入应用日志、进程退出记录和服务重启记录。系统按统一时间排序事件，
识别错误日志、非零退出和随后重启之间的时间关系，并在报告中引用相关证据。

### 3.2 性能退化

用户导入 CPU、内存、延迟快照以及告警日志。系统在指定时间窗口内关联资源
异常与请求延迟，输出可核查的事件序列，而不是直接断言某个指标就是根因。

### 3.3 配置变更故障

用户导入配置变更记录、应用日志和健康检查结果。系统展示变更前后的关键事件，
标记紧随变更出现的故障症状，并明确区分“观察到的事实”和“待验证的假设”。

## 4. 输入

首版接受用户明确提供的本地静态证据：

- 每行一个事件的 JSONL 文件。
- 带时间戳或不带时间戳的纯文本日志。
- 描述案件名称、证据来源和采集说明的案件元数据。
- 用于演示和测试的脱敏样例数据。

首版不在后台主动扫描主机，也不要求管理员权限。夹具字段见 `samples/README.md`。
JSONL 与固定格式文本适配器已提供统一字段、证据位置和资源映射；服务/实例粒度边界
见 `reapplication-design.md`。未声明映射的供应商格式仍不自动猜测，案件级文件 I/O
和完整报告工作流留在后续范围。

## 5. 输出

- 证据清单：文件标识、来源、大小、摘要和校验状态。
- 统一时间线：标准化时间、严重级别、来源和原始事件引用。
- 诊断发现：命中规则、相关事件、置信说明和证据引用。
- Markdown 报告：供人工阅读和故障复盘。
- JSON 报告：供后续工具处理和自动化测试。

## 6. 核心不变量

1. **不静默修改原始证据**：解析和分析只产生派生数据。
2. **结论可以回指证据**：每条诊断发现至少引用一个已导入证据项。
3. **事实与假设分离**：观察值、规则命中和根因假设使用不同状态表达。
4. **输出可复现**：相同输入和相同配置必须产生顺序与内容一致的报告。
5. **失败必须可见**：无法解析、时间缺失和完整性校验失败不能被当作正常事件跳过。

## 7. 预期失败方式

- 文件不存在、无法读取或在分析过程中发生变化。
- JSONL 行格式错误、字段缺失或字段类型不匹配。
- 时间戳无效、时区不明确，或者部分日志没有时间戳。
- 同一事件被重复导入，或不同来源产生相同时间的事件。
- 证据摘要与清单不一致。
- 规则没有足够证据支持结论，或多个规则给出冲突假设。
- 报告目标路径不可写。

这些情况必须返回结构化错误或带来源位置的诊断；不得崩溃后只留下无上下文的
错误文本。

## 8. 首版范围

### 必须交付

- 案件、证据、事件和诊断发现的数据模型。
- JSONL 与纯文本日志导入。
- 时间、严重级别和来源标准化。
- 证据清单和完整性校验。
- 确定性的统一时间线与筛选。
- 可解释的规则匹配和有限的事件关联。
- Markdown 与 JSON 报告。
- 可运行的命令行入口和三个端到端样例。
- 核心路径测试、持续集成、使用文档和开源许可证。

### 明确不做

- 不实时监控主机，不驻留后台采集数据。
- 不读取内存镜像、磁盘镜像或网络数据包。
- 不自动获取管理员或 root 权限。
- 不提供司法取证合规承诺或不可否认性保证。
- 不使用机器学习模型自动宣判根因。
- 不在首版开发 GUI、远程服务、数据库或多用户权限系统。
- 不为了制造提交数量而创建空提交或机械拆分同一个实现。

## 9. 验收样例

### 样例 A：异常退出

给定错误日志、非零退出记录和随后发生的重启事件，分析结果应按时间展示三者，
生成“异常退出后重启”的规则命中，并能从命中结果定位回原始日志行。

### 样例 B：损坏证据

给定一份已建立清单、随后被修改的证据文件，校验必须失败，分析不得把该证据
标记为已验证。

### 样例 C：配置变更相关性

给定配置变更事件以及短时间内出现的健康检查失败，报告应展示二者的时间关系，
将“配置变更可能相关”标记为假设，而不是已确认根因。

### 样例 D：确定性

对同一案件连续运行两次，在忽略用户显式指定的输出路径后，Markdown 和 JSON
报告内容必须一致。

## 10. 首版成功标准（目标，尚未全部达成）

- 三个使用场景都能通过仓库内脱敏样例一条命令复现。
- 损坏证据、畸形输入和缺失时间均有自动化负向测试。
- 所有诊断发现都能追溯到证据项和原始位置。
- 新环境可以按照 README 完成检查、测试和示例运行。
- 项目至少形成 10 个有独立价值且可验证的真实提交。

## 11. 术语

| 术语 | 定义 |
| --- | --- |
| 案件（Case） | 一次故障调查及其证据、配置和输出的逻辑集合。 |
| 证据项（Evidence Item） | 用户导入的一个原始文件及其来源和完整性信息。 |
| 原始记录（Raw Record） | 从证据项中读取、尚未标准化的一条记录。 |
| 事件（Event） | 经过解析和标准化、可进入时间线的记录。 |
| 发现（Finding） | 规则依据一组事件生成的可解释分析结果。 |
| 事实（Observation） | 能由导入证据直接支持的描述。 |
| 假设（Hypothesis） | 需要进一步验证的可能解释，不等同于已确认根因。 |
| 证据引用（Evidence Reference） | 从事件或发现定位回证据项及原始位置的信息。 |
| 证据清单（Manifest） | 记录证据元数据和完整性摘要的清单。 |
| 取证舱（Cockpit） | 汇集、校验、关联并呈现故障证据的离线工作空间。 |
